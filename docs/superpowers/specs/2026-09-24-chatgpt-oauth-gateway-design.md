# ChatGPT OAuth gateway and private plugin design

Date: 2026-09-24
Status: Design approved in conversation; implementation pending written-spec review
Owner: eitaar
Repository: `eitaar/driichi`

## Goal and scope

Let the owner's ChatGPT account connect to the self-hosted driichi MCP server through a private plugin using OAuth, while existing Pi MCP and MJAI clients continue to authenticate with Bot Tokens. The first release supports one driichi administrator and one ChatGPT connection. It does not add ordinary user accounts, public plugin distribution, autonomous server-initiated LLM turns, or an in-chat table UI.

Success means the owner can authenticate in ChatGPT, join a Room, read only that MCP Participant's private state, submit a legal action, and leave. Invalid, expired, wrong-audience, or revoked OAuth credentials must fail before reaching the MCP handler. Existing `/mcp` and MJAI contracts must pass their regression suites without changing client configuration.

## Existing boundary

The Axum server mounts `/mcp` in `crates/double_riichi_server/src/http.rs`. `McpRuntime::handle` authenticates a raw Bot Bearer credential on every request, checks the origin and `mcp-session-id` binding, then inserts `McpAuth(token_id)`. Room participants are keyed by Bot Token ID plus Room code. The current tool set is `join_room`, `leave_room`, `submit_action`, `wait_for_turn`; private state, public state, and history are MCP Resource templates. The stdio `driichi-mcp` bridge uses the existing Bot Token path. The sample server configuration binds to localhost and uses an HTTP public origin; neither is a ChatGPT-reachable OAuth endpoint.

## Selected architecture

Add an optional, in-process OAuth gateway to `double_riichi_server`, exposed only when a public HTTPS origin and a separate, active Bot Token for this gateway are configured. Mount `/chatgpt/mcp` alongside the unchanged `/mcp`. OAuth is handled at the new route boundary; after validating the OAuth access token, the gateway replaces the inbound Authorization header with its dedicated Bot Token and passes the same request to the existing MCP runtime. The gateway must strip user-supplied internal identity headers and never expose the raw Bot Token in a response, log, OAuth token, plugin archive, or URL. If an Origin header is present, validate it against a narrow configured allowlist at the gateway; after validation remove it before invoking the existing handler, whose same-origin check is designed for /mcp clients. Reject any unrecognized Origin. Keep the MCP transport streaming, including SSE, and preserve session IDs and DELETE semantics.

Only the administrator can approve access. CIMD identifies the ChatGPT OAuth *client*, not the human account; the authorization screen must validate the existing driichi admin identity and obtain explicit consent. The gateway uses one dedicated Bot Token. Its revocation disables the downstream MCP calls, and authorization cannot be silently re-bound to a different Bot Token. No Bot Token is generated by OAuth or shown to ChatGPT.

Alternative evaluated: a separate HTTP proxy could keep OAuth code outside the server, but would duplicate MCP stream/session handling, admin identity, revocation, and deployment configuration. A shared public `/mcp` route with dual-token parsing would increase risk of accidentally accepting OAuth tokens on the Pi path. The selected separate route reuses the existing server runtime while preserving the old credential boundary.

## OAuth contract

- Protected resource identifier: exact configured `https://<public-origin>/chatgpt/mcp`. Publish RFC 9728 metadata at `/.well-known/oauth-protected-resource/chatgpt/mcp`; include its URL in `WWW-Authenticate` on an unauthenticated MCP request. Its `authorization_servers` value equals the issuer exactly.
- Publish authorization-server metadata at `/.well-known/oauth-authorization-server`. Set `client_id_metadata_document_supported: true`, advertise `code_challenge_methods_supported: ["S256"]` and `token_endpoint_auth_methods_supported: ["none"]`, and implement authorization-code and refresh-token grants. No DCR or client secret for the first release.
- Accept only the ChatGPT CIMD client URL returned by its connection management page, fetch and validate the HTTPS metadata with a strict trusted-origin allowlist, and validate the exact redirect URI published there. Never treat a caller-controlled `client_id` URL as an unrestricted network fetch. Bind the authorized client, redirect URI, scope, resource, admin identity and PKCE challenge to a single-use short-lived code.
- Implement issuer identification: advertise `authorization_response_iss_parameter_supported: true` only when every authorization response, including errors, carries the exact issuer `iss`. Use the exact ChatGPT redirect URI for this mode. Keep issuer and resource stable across deployments.
- Authorization requires an existing admin session or an admin login using the same credential verifier and login throttling as the current server. A consent page names driichi, the requested access, and the connected ChatGPT client. Protect the login and consent transition against CSRF. No login credential is sent to ChatGPT.
- Require `resource` at both authorization and token endpoints, and bind access/refresh tokens to that exact MCP resource. Issue opaque access tokens (10-minute lifetime) and rotating refresh tokens (30-day maximum lifetime); persist only hashes, client/subject/scope/audience/expiry/revocation metadata in SQLite. Reuse of a rotated refresh token revokes its token family. Use one scope, `driichi:play`, enforced on every MCP request.
- Reject missing or bad tokens with HTTP 401 and a discoverable Bearer challenge; reject insufficient scope with HTTP 403. Reject a disabled Bot Token, changed gateway credential, malformed session, invalid origin, or non-HTTPS configured public origin. Redact credential values in telemetry.

## Tool surface and behavior

Preserve the four existing MCP tools and three Resource templates for Pi. Add a read-only `get_my_state` tool to the MCP handler, returning the same private projection as the existing participant state Resource after the normal session and Bot Token binding checks. This is additive for existing clients and gives ChatGPT a directly callable state read. Output contains the current revision and legal decisions, without other players' concealed tiles. Mark it read-only; mark state-changing tools accurately.

The intended interactive sequence is `join_room` -> `get_my_state` -> `submit_action` -> `get_my_state`, with optional `wait_for_turn` and `leave_room`. Every action remains subject to driichi's existing legal-decision checks. Resource subscriptions can remain available to Pi; the private ChatGPT plugin does not promise automatic play while no conversation turn is running. Do not add scheduled polling or a server-to-ChatGPT callback.

The plugin package is `driichi-chatgpt`: a root Agent Plugins 1.0 manifest, a portable `mcp.json` pointing to the actual deployed HTTPS `/chatgpt/mcp` URL, and one skill describing the interactive workflow and avoiding disclosure of hidden state or credentials. Package it only when that actual endpoint is configured and verified. Keep all secrets on the server; none belong in the plugin archive.

## Deployment and verification

The operator configures a durable public HTTPS origin and secure inbound transport (for example, a TLS-terminating reverse proxy) and supplies the dedicated Bot Token as the process secret `DRIICHI_CHATGPT_BOT_TOKEN`. The server verifies this token is active at startup; deployment must configure the exact ChatGPT CIMD metadata URL and callback URI visible in the connection management page. The gateway remains disabled unless configuration is complete. Keep `/mcp` available for existing Bot Token clients. A localhost-only HTTP instance is insufficient for a live ChatGPT connection.

Verify metadata discovery, exact issuer and redirect matching, CIMD restrictions, PKCE success/failure, one-time code redemption, resource/audience/scope checks, refresh rotation/reuse, admin-only consent, CSRF protection, Bot Token revocation, secret redaction, and OAuth-only rejection on `/mcp`. Exercise streamed MCP initialization, session reuse, resource privacy, state tool, action submission and DELETE through both paths. Run the existing Rust workspace and bridge/MJAI regression tests. Finally test the real HTTPS endpoint and OAuth login from ChatGPT Developer Mode before creating the plugin.
